# Техническое задание: локальная «Студия бизнес-процессов»

Версия требований: 1.0. Дата: 20 августа 2026 года.

## 1. Цель

Сделать комплект, с которым сотрудник, впервые увидевший BPMN, может без ИИ:

1. запустить проект одним двойным щелчком;
2. создать не пустой файл, а готовый осмысленный процесс;
3. изменить схему мышью в графическом редакторе;
4. получить понятные ошибки без XML, JSON, хешей и внутренних кодов;
5. построить карту Archify одним действием;
6. оформить переход в существующий, будущий или пока неизвестный процесс;
7. передать разработчику стандартный BPMN 2.0 и сопровождающие материалы;
8. при необходимости дать любому MCP-совместимому агенту тот же безопасный
   доступ к процессам, не делая ИИ обязательным.

## 2. Пользователи

### Сотрудник или владелец процесса

Читает карту, проверяет фактический маршрут, отвечает на вопросы и фиксирует
решение. Не обязан знать BPMN-термины.

### Аналитик

Редактирует BPMN, карточку, крупные этапы карты и межпроцессные связи. Видит
подробные диагностические сведения по запросу.

### Разработчик

Получает нейтральный `process.bpmn`, метаданные, вопросы, решения, основания и
карту. Создаёт отдельный исполняемый адаптер под выбранный движок.

### Агент

Через локальный MCP читает каталог, BPMN, вопросы и межпроцессные связи, создаёт
черновик, сохраняет XML с проверкой версии, запускает проверку и строит Archify.
Не может сам подтвердить решение владельца или обойти правила пакета.

## 3. Пользовательский сценарий

```text
Создать → Нарисовать → Проверить → Построить карту → Опубликовать черновик
              ↑                                         │
              └────────────── Доработка ─────────────────┘
                                      → Решение владельца
```

На каждом экране должна быть одна выделенная рекомендуемая кнопка. Расширенные
действия не удаляются, но находятся в блоке «Дополнительно».

## 4. Основной интерфейс

Запуск: `ОТКРЫТЬ-BPMN-РЕДАКТОР.cmd`.

Локальная Студия открывается на случайном порту `127.0.0.1` и содержит:

- сверху рабочей области — «Новая схема», «Открыть BPMN», «Сохранить»,
  «Сохранить как…», «Проверить» и «Дополнительно»;
- в центре — большой графический холст BPMN;
- в расширенном режиме — каталог процессов и вкладки «Карта для человека» и
  «Карточка и вопросы»;
- на вкладке BPMN — графический редактор, кнопки масштаба и контекстная правая
  панель «Связать с другим процессом», которая открывается только для выбранной
  задачи или Call Activity;
- на вкладке «Карточка и вопросы» — готовность, рекомендуемое следующее
  действие, результаты проверки, межпроцессные связи, основные факты и путь до
  рабочего процесса;
- технические подробности — внутри раскрываемого блока результата проверки, а
  не в постоянно видимом журнале.

В текущей версии вкладка «Карточка и вопросы» является сводкой и не редактирует
содержимое `process-card.md`, `questions.json`, `decisions.json` и
`evidence/README.md`. Формы для них относятся к следующей версии.

Технические ID не показываются в обычном режиме. Название процесса и файла
может быть любым; подписи шагов, ролей, результатов и условий должны быть
понятны читателю. Знак bpmn.io остаётся видимым согласно лицензии.

## 5. Функциональные требования

### 5.1 Создание

- «Новая схема» сразу открывает осмысленную основу без анкеты;
- имя и папку пользователь выбирает в системном окне «Сохранить как…»;
- название может быть любым непустым однострочным текстом;
- полный пакет создаётся только по отдельному действию в «Дополнительно»;
- стартовая BPMN-модель уже содержит начало, действие, решение и понятные исходы;
- пакет получает статус черновика и не считается утверждённым.

### 5.2 Графическое редактирование

- используется закреплённый `bpmn-js`;
- поддерживаются задачи, события, развилки, участники, дорожки и связи BPMN;
- подпись элемента меняется непосредственно на схеме;
- undo/redo работают средствами modeler;
- сохранение выполняется только после успешного разбора BPMN XML;
- конкурентное сохранение проверяется по SHA-256 исходной версии;
- запись выполняется атомарно и не оставляет частичный файл;
- созданные редактором случайные ID либо приводятся к смысловым ID безопасно,
  либо сохранение блокируется понятным списком элементов для исправления.

### 5.3 Проверка

Проверка выбранного процесса должна возвращать машинный результат и русское
объяснение:

- BPMN XML читается;
- подписи шагов, ролей, исходов и условий понятны читателю;
- видимые технические ID не подменяют подписи элементов;
- технические ID стабильны и смысловые;
- все развилки и исходящие ветки подписаны;
- Call Activity согласованы с `target_process_id`;
- независимая передача оформлена сообщением;
- карта и bindings не ссылаются на удалённые элементы;
- хеши, решение владельца и производные материалы актуальны;
- открытые блокирующие вопросы не скрыты.

### 5.4 Межпроцессные переходы

Для каждого перехода пользователь выбирает один из трёх честных вариантов:

1. готовый процесс из каталога;
2. карточка будущего процесса с зарезервированным постоянным ID;
3. цель пока не определена.

Вызов с возвратом моделируется Call Activity. Независимая передача моделируется
сообщением. После регистрации целевого процесса все навигаторы пересобираются,
поэтому старая карточка автоматически заменяется готовой схемой при совпадении ID.

В первой версии мастер автоматически создаёт только Call Activity. Message
handoff остаётся ручным BPMN-сценарием и не имитируется вызовом с возвратом.

### 5.5 Archify одним действием

Кнопка «Построить карту Archify» запускает один адаптер:

1. берёт вручную подготовленный `process-map.workflow.json`, если он существует;
2. иначе создаёт детерминированный автоматический черновик из BPMN;
3. строит и проверяет `process-map.bindings.json`;
4. выполняет Archify `validate` и `deliver` закреплённой версией;
5. атомарно принимает только полностью прошедший результат;
6. сохраняет receipt с версией и SHA-256 входов/выходов;
7. открывает автономный HTML без внешних шрифтов и сети.

Автоматический результат явно маркируется как черновик. Ручное укрупнение
этапов аналитиком не перезаписывается автоматикой без подтверждения.

### 5.6 Жизненный цикл

- `draft` — технический черновик;
- `review-ready` — пакет готов к содержательной проверке;
- `approved/canonical` — точная версия утверждена владельцем;
- `rework` — версия возвращена на доработку;
- `rejected` — версия отклонена.

Изменение BPMN, карточки или оснований после решения делает старое решение
неактуальным и возвращает пакет на повторную проверку. Локальная фиксация решения
является заявлением пользователя; полномочия подтверждаются защищённым approval
Merge Request в GitLab.

### 5.7 Передача разработчику

Студия не должна называть нейтральную схему исполняемой. Пакет разработчика
доступен только для актуальной утверждённой версии без блокирующих вопросов.

Минимальный состав:

- `process.bpmn`;
- `process.meta.json`;
- карточка процесса;
- вопросы и решения;
- основания;
- карта и bindings;
- manifest с SHA-256;
- инструкция по созданию отдельной копии под движок.

### 5.8 Нативный MCP для агентов

- используется официальный MCP SDK и локальный transport `stdio`;
- сервер не требует облачного сервиса и не открывает сетевой порт;
- каталог и конкретные пакеты доступны как MCP resources;
- инструменты покрывают чтение, создание черновика, сохранение BPMN с
  `expectedSha256`, проверку, построение Archify, обновление и техническую
  регистрацию черновика;
- абсолютные пути от клиента не принимаются: агент передаёт только безопасный
  `slug` процесса;
- ошибки имеют стабильный код, короткое русское объяснение и безопасные детали;
- сервер не предоставляет инструмент утверждения или фиксации решения за
  владельца процесса;
- конфигурации для Codex, Claude Desktop/Code и Cursor документируются, но не
  записываются в пользовательские настройки автоматически.

## 6. Архитектура

```text
человек                         агент
   │                              │
CMD → браузер → bpmn-js       MCP stdio
   └───────────────┬──────────────┘
           Process Workspace Core
       ┌───────────┼──────────────┐
     пакеты     проверки      транзакции
       │           │              │
       └────── Adapter Host ───────┘
                │            │
             Archify      движки позже
```

Минимальный программный контракт:

```text
inspect(slug?) → состояние, блокеры, рекомендуемое действие, revision
execute(action, slug, expectedRevision, input) → новый снимок или ошибка
```

Клиент не передаёт абсолютные пути и не устанавливает желаемый статус напрямую.
Core повторно вычисляет допустимость действия из файлов пакета.

## 7. Безопасность и надёжность

- server слушает только `127.0.0.1`;
- сессия имеет случайный token;
- запросы с чужим Origin отклоняются;
- из UI принимаются только известные действия и проверенный slug;
- пользовательский текст не включается в shell-команду;
- все записи используют staging, ожидаемый hash и atomic rename;
- операции изменения сериализуются для одного процесса;
- rollback восстанавливает файлы байт-в-байт;
- плагины получают снимок и staging, а не право произвольно писать в пакет;
- сеть не нужна после подготовки зависимостей;
- секреты, ПДн и локальные абсолютные пути не попадают в Git.

## 8. Совместимость

- существующий процесс `skupka-zolota` открывается без миграции;
- его XML не меняется до явного сохранения;
- в корне остаётся один CMD-запуск Студии, а npm-команды — интерфейс сопровождения;
- `.bpmn` открывается Camunda, Bizagi и другими BPMN 2.0 редакторами;
- vendor-specific execution extensions не попадают в нейтральный источник.

## 9. Критерии приёмки первого релиза

1. `ОТКРЫТЬ-BPMN-РЕДАКТОР.cmd` запускает Студию одним двойным щелчком.
2. Первый экран показывает «Новая схема», «Открыть BPMN» и графический холст.
3. Новая схема создаётся без анкеты, а название и папку выбирает пользователь.
4. Стартовая схема осмысленна и редактируется встроенным modeler.
5. Сохранение защищено от устаревшей вкладки и частичной записи.
6. Проверка показывает русские сообщения и не требует знания путей/JSON.
7. Archify-карта строится одной кнопкой из закреплённого runtime.
8. На новом компьютере одинаковые входы дают проверяемый результат и receipt.
9. На диаграмме обычная задача преобразуется в Call Activity; пользователь
   выбирает готовый, будущий или пока неизвестный процесс, а готовая цель
   открывается из Студии и навигатора.
10. MCP-клиент получает каталог и BPMN и выполняет безопасную проверку через
    официальный протокол; команды утверждения владельца нет.
11. Весь базовый сценарий работает без ИИ.
12. Нет внешних сетевых запросов интерфейса и шрифтов.
13. Unit, contract, MCP integration, browser smoke, determinism и `verify:all`
    проходят.
14. После тестов рабочее дерево не загрязняется случайными файлами.
15. Commit/push выполняются только после отдельного подтверждения пользователя.

## 10. Следующие версии

- формы для карточки, ролей, вопросов и оснований без ручного Markdown/JSON;
- semantic diff при импорте из Bizagi/Camunda;
- адаптеры Camunda 8 и Flowable в отдельные исполняемые копии;
- переносимый подписанный Windows-дистрибутив с Node runtime;
- необязательный ИИ-помощник, работающий только через тот же проверяемый Core.
