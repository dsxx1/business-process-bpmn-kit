# Как добавить новый процесс

Ниже — основной путь для человека, который впервые работает с BPMN. Схема
создаётся и редактируется в локальной Студии мышью; вручную копировать шаблон,
править XML или устанавливать отдельный BPMN-редактор не нужно.

## 1. Подготовьте проект и запустите Студию

1. Установите [Node.js 22.12 или новее](https://nodejs.org/), если его ещё нет.
2. Клонируйте проект или скачайте архив из GitLab и распакуйте его.
3. Дважды щёлкните `ОТКРЫТЬ-BPMN-РЕДАКТОР.cmd` в корне проекта.

При первом запуске мастер установит закреплённые зависимости. После установки
Студия, проверки и построение карты работают локально на `127.0.0.1`, без ИИ и
без передачи схемы во внешний сервис.

## 2. Создайте черновик

Если нужна только схема, нажмите **«Новая схема»** и сохраните `.bpmn` под любым
именем в выбранную папку. Никакой пакет и запись в реестре при этом не создаются.

Если процесс должен войти в общий проект:

1. Откройте **«Дополнительно» → «Показать процессы проекта»**.
2. Нажмите **«Добавить процесс в проект»**.
3. Введите любое удобное название. Внутреннее имя папки Студия предложит сама.
4. Нажмите **«Создать основу»**.

Студия создаст `processes/<короткое-название>`, готовую стартовую BPMN-схему,
смысловые технические идентификаторы и остальные файлы пакета. Существующий
процесс не перезаписывается. Новый пакет остаётся черновиком и не появляется в
общем реестре, пока человек его не проверит и явно не зарегистрирует.

## 3. Нарисуйте маршрут

Откройте вкладку **«BPMN-схема»**. Стартовая модель уже содержит начало,
действие, развилку и понятные результаты. Переименуйте и перестройте её под
фактическую работу:

- начало — наблюдаемый факт, например «Получена заявка»;
- действие — глагол и объект, например «Проверить документы»;
- дорожка — роль, которая отвечает за действие;
- развилка — понятный вопрос, а каждый выход подписан «Да», «Нет» или другим
  однозначным условием;
- завершение — конкретный результат, а не слово «Конец»;
- вызов процесса — отдельный процесс, после которого текущий маршрут
  продолжается.

Дважды щёлкните подпись блока, чтобы изменить её. Выделите блок, чтобы добавить
следующий элемент или изменить его тип. Кнопка **«Первый раз в BPMN?»** объясняет
основные обозначения. Сохраняйте изменения кнопкой **«Сохранить»** или
`Ctrl+S`.

Канонический источник — `bpmn/process.bpmn`. Не заменяйте его рисунком из
diagrams.net: картинка не является переносимой BPMN-моделью для движка.
Подробная инструкция: [графическое создание процесса](ГРАФИЧЕСКОЕ-СОЗДАНИЕ-ПРОЦЕССА.md).

## 4. Свяжите следующий процесс

Если один шаг вызывает другой бизнес-процесс и после него текущий маршрут
продолжается:

1. Выберите на схеме обычную задачу или уже созданный блок вызова. Справа
   автоматически откроется панель **«Связать с другим процессом»**.
2. Для обычной задачи нажмите **«Сделать этот шаг вызовом другого процесса»**.
   Студия сохранит название и стрелки и заменит блок стандартным BPMN-элементом
   Call Activity.
3. Выберите один из трёх честных вариантов:
   - **«Процесс уже есть»** — выбрать зарегистрированный процесс;
   - **«Процесс появится позже»** — сохранить любое непустое название и
     карточку-заготовку;
   - **«Пока неизвестно»** — зафиксировать неопределённость, ничего не угадывая.
4. Напишите понятную русскую подпись перехода и нажмите **«Сохранить связь»**.

Студия атомарно обновит BPMN и служебные метаданные: либо сохранятся оба файла,
либо ни один. Готовая цель открывается действием **«Открыть процесс»**, а будущая
— действием **«Открыть карточку будущего процесса»** на вкладке
**«Карточка и вопросы»**.

Чтобы убрать вызов, снова выберите его на схеме и нажмите **«Удалить связь»**.
После подтверждения Студия сама удалит метаданные и превратит Call Activity
обратно в обычную задачу. Перенести существующую связь на другой блок нельзя:
удалите её и создайте заново на нужном шаге.

Текущий мастер безопасно оформляет вызов с возвратом. Независимая передача
управления сообщением имеет другой BPMN-смысл и пока настраивается только
экспертом. Полный контракт: [переходы между BPMN-процессами](ПЕРЕХОДЫ-МЕЖДУ-BPMN-ПРОЦЕССАМИ.md).

## 5. Завершите содержательную часть пакета

Вкладка **«Карточка и вопросы»** показывает готовность, результаты проверки и
межпроцессные связи. В текущей версии она ещё не редактирует содержимое
карточки, вопросов и оснований. Откройте папку
`processes/<короткое-название>` в Проводнике и заполните обычным текстовым
редактором:

- `process-card.md` — цель, границы, запуск, результат, роли, основной маршрут
  и исключения;
- `bpmn/questions.json` — нерешённые вопросы владельцу;
- `bpmn/decisions.json` — только действительно принятые решения;
- `evidence/README.md` — источники фактов и границы подтверждённости.

Карточка и BPMN должны описывать один маршрут. Если они расходятся, процесс ещё
не готов к регистрации. Служебный `process.meta.json` для переходов вручную не
правьте: используйте графическую панель из предыдущего шага.

## 6. Проверьте схему и постройте карту

1. Сохраните BPMN и нажмите **«Проверить»**.
2. Откройте вкладку **«Карточка и вопросы»**, прочитайте первое замечание и
   исправьте все ошибки.
3. Откройте вкладку **«Карта для человека»** и нажмите
   **«Построить карту Archify»**.
4. Просмотрите карту. Для сложного процесса автоматический результат остаётся
   черновиком до проверки аналитиком.

Archify создаёт удобное представление для чтения, но не заменяет
`bpmn/process.bpmn`. Техническая проверка также не означает, что содержание
утверждено владельцем.

## 7. Зарегистрируйте технический черновик

Когда проверка проходит, на вкладке **«Карточка и вопросы»** нажмите
**«Зарегистрировать процесс»**. Студия повторно проверит комплект, построит
производные файлы и добавит черновик в общий реестр и каталог. Если обязательный
шаг завершится ошибкой, регистрация не состоится.

Регистрация — техническая публикация для совместной проверки, а не
бизнес-утверждение. Для уже зарегистрированного процесса эта же кнопка называется
**«Обновить комплект процесса»**.

Эквивалентные команды для специалиста:

```powershell
Set-Location tools\bpmn
npm run register:process
npm run update:process
```

## 8. Зафиксируйте решение владельца

После содержательной проверки маршрута, ролей, исключений и переходов запустите
вместе с уполномоченным владельцем:

```powershell
Set-Location tools\bpmn
npm run decision:owner
```

Мастер предложит утвердить точную текущую версию, вернуть её на доработку или
отклонить. Утвердить процесс с открытыми блокирующими вопросами нельзя. Решение
связывается с контрольными суммами BPMN, карточки и оснований и не переносится
на изменённую версию.

Локальная команда фиксирует заявление, но не проверяет личность и полномочия
человека. Перед слиянием изменение должен дополнительно подтвердить
уполномоченный владелец через защищённое согласование Merge Request в GitLab.

## 9. Обновляйте процесс после изменений

После любой правки зарегистрированного процесса:

1. сохраните и проверьте схему в Студии;
2. заново постройте Archify-карту;
3. нажмите **«Обновить комплект процесса»**;
4. если версия изменилась после решения владельца, снова проведите
   содержательную проверку и запустите `npm run decision:owner` в `tools/bpmn`.

Прежнее решение останется в истории, а новая версия вернётся на повторную
проверку. Для итоговой технической проверки можно запустить:

```powershell
Set-Location tools\bpmn
npm run verify:all
```

## Экспертный путь без Студии

Ручной путь сохранён для аналитика, разработчика и CI:

1. В `tools/bpmn` выполните
   `node create-process-package.mjs --title "Любое название" --slug example`.
2. Откройте созданный `bpmn/process.bpmn` во встроенной Студии, Camunda Desktop Modeler, Bizagi или
   другом BPMN 2.0-совместимом редакторе.
3. Заполните карточку, вопросы, решения и основания в файлах пакета.
4. Запустите `npm run verify:all`, затем `npm run register:process` или
   `npm run update:process`.

Camunda редактирует `.bpmn` напрямую. Bizagi хранит рабочую модель в
собственном формате, поэтому после каждой правки нужно заново экспортировать
BPMN 2.0 в `bpmn/process.bpmn`. Ручное изменение
`process.meta.json`, `calledElement` и XML допустимо только для специалиста,
который понимает пакетный контракт и после этого запускает полную проверку.

## Что получает разработчик

Разработчик берёт тот же нейтральный `bpmn/process.bpmn`, а не картинку и не
файл конкретного редактора. Каноническая бизнес-модель имеет
`isExecutable=false`. Для исполнения создаётся отдельная копия под Camunda,
Flowable или другой движок с обработчиками задач, переменными, формами и
техническими ошибками.
